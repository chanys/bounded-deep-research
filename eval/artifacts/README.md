# eval/artifacts

This folder is the **output tray** for building AnswerTrail's Phase 4 evaluation.
Everything here is generated by the scripts in the `eval/` package (nothing is hand-written), and everything is for one YouTube channel, **code4AI**.

If you're new to this folder, the key idea is that building an evaluation happens in stages, and the files below are the outputs of those stages.
Roughly, the work goes: **understand the corpus -> turn it into good test questions -> prepare reference answers to grade against.**
The files group onto those steps, plus one older approach we have since replaced but kept as a record.

### A note on what's in git

Most files here are **bulk generated data and are gitignored** - they are large, and they can be regenerated from the scripts (or restored from backup).
Only the small, human-reviewed artifacts are committed to git: the final query sets (`queryset_*.jsonl`), the readable corpus inventory (`inventory_code4AI.md`), the methods record (`generation_conditions.md`), and the longitudinal candidate shortlist (`longitudinal_shortlist.md`).
The larger `*_sample.md` and `*_index.md` renders are review aids that stay untracked (regenerable from the scripts).

### Naming conventions

- `*_code4AI` - the file is for the code4AI channel.
- `*_sample.md` / `*_chunks.md` - a **human-readable render** of a run, made so a person can eyeball the results without reading raw JSON.
- `*_claimslice*` - belongs to the **current** query-building pipeline (the "claim-derived" one described below).

## 1. Corpus inventory - what the videos actually contain

Before you can write test questions, you need a map of the corpus.
These files are that map, built once and reused by everything downstream.

- **`summaries_code4AI.jsonl`** - one record per video, holding a short summary, the video's key points, its topics and named entities, and any questions the creator asks out loud. This is the foundational description of each video.
- **`inventory_code4AI.json`** - a machine-readable map of the whole corpus: it groups the videos into topic clusters, summarizes each cluster, and records which cluster and publish date each video has.
- **`inventory_code4AI.md`** - the same inventory written for a human to read (committed to git).
- **`questions_code4AI.jsonl`** - every question the creator poses across all the transcripts, de-duplicated, with a note of which videos each came from.

## 2. Claim-derived query pipeline - the current way we build questions

This is the pipeline we use now.
Its central idea: build the test questions from small, atomic **claims** pulled straight from the transcripts, rather than from the summaries.
Why it matters - a summary is also something a retrieval system might index, so a question written from a summary could "leak" its source; questions written from independent claims avoid that.

The flow is: **extract claims -> compose questions from them -> (later) verify and pick the final set.**

> **Which file do I open to review the candidates?**
> Open the `*_sample.md` render for that question type - it is the human-readable review file:
> **factual -> `factual_claimslice_sample.md`**, **comparative -> `comparative_claimslice_sample.md`**, **longitudinal -> `longitudinal_claimslice_sample.md`**.
> The matching `query_candidates_*_claimslice.jsonl` is the exact machine data those renders are built from; you only need it if a tool is consuming the candidates, not for eyeballing.

- **`claims_code4AI.jsonl`** - the claim inventory: every concrete claim each video makes, each tied to the exact transcript chunks that state it, and dated (~26,000 claims). This is the raw material for all the questions below.
- **`query_candidates_factual_claimslice.jsonl`** - the **factual** candidate questions as machine data (source of truth). Each record carries the question, the video and claim it came from, and the claim's text as a draft answer. (To review these by eye, open the sample file below, not this one.)
- **`factual_claimslice_sample.md`** - **the file to review for factual candidates.** A readable view of every factual candidate: for each question it shows the chosen claim and the full list of claims from that video, so you can judge whether the best claim was picked.
- **`factual_claimslice_chunks.md`** - a one-off review aid: the raw transcript text sitting behind the claims chosen for a set of factual questions, so you can check the claims are faithful to what was actually said.
- **`query_candidates_comparative_claimslice.jsonl`** - the **comparative** candidate questions as machine data (source of truth). Each is built from a *pair* of claims about two different named things (e.g. two models on the same benchmark), so answering requires evidence from both videos. (To review by eye, open the sample file below.)
- **`comparative_claimslice_sample.md`** - **the file to review for comparative candidates.** A readable view of every comparative candidate, plus the run's health stats: the funnel (how many pairs were generated, judged, accepted), the diversity caps, the stop-list, and a sample of rejected pairs with reasons.
- **`groundable_claims.json`** - a cache that records, for each claim, whether it is substantive enough to build a question from, versus content-free setup or narration (e.g. "the creator tests two models"). This saves re-deciding the same claim twice and is shared across question types.
- **`groundable_claims_code4AI.json`** - an older, video-keyed version of that same cache, kept because its answers are still valid and save re-computation.
- **`query_candidates_longitudinal_claimslice.jsonl`** - the **longitudinal** candidate questions as machine data (source of truth). Each asks how the creator's position or results developed *over time* on one topic, built from a dated thread of claims across several videos; it carries trajectory-level "must-say" points plus dated, chunk-anchored milestone slots as its draft gold. (To review by eye, open the sample file below.)
- **`longitudinal_claimslice_sample.md`** - **the file to review for longitudinal candidates.** A readable view of every candidate with the run funnel; the few flagged items (kept for human review) are listed first, then the accepted candidates ordered by leak-risk.

**Longitudinal post-run triage.** The longitudinal run accepts far more candidates than the final set needs (~500), because the pool mixes genuine trajectories with topic-recurrence "collections", so three extra files help a human narrow them down. None of these labels, gates, or drops anything on its own - they are reading aids, and every candidate stays in one list.

- **`longitudinal_arc_index.md`** - a reading index of all accepted candidates, grouped into clusters of near-duplicate topics (so you keep one question per story), with a simple keyword-based sort hint inside each cluster and the span-defective candidates flagged at the bottom. An LLM "arc scorer" was tried to label each candidate as a genuine trajectory versus a loose collection, but it failed its calibration gate and was abandoned, so this index uses the deterministic keyword hint only.
- **`longitudinal_shortlist.md`** - a curated shortlist (two tiers plus a seeded random spot-check of dropped items) from an advisory read of all the candidates, recorded for the final human pick; human verification is still pending.
- **`arc_scores_cache.json`** / **`longitudinal_advisory_cache.json`** - caches behind the abandoned arc scorer and the advisory leak-risk sort, kept so the work is not recomputed.

Still to come (not built yet): checking each candidate's evidence actually holds up (grounding, all three tiers together) and the final human pick of the questions per type.

## 3. Legacy query pipeline - the older approach, kept for the record

Before the claim-derived pipeline, questions were generated from the Stage 1 **summaries**.
That approach has been superseded, but its files are kept: the final `queryset_*` files are still a committed query set, and the intermediate files are the paper trail showing how it was built.

The flow was: **generate candidates -> ground them -> score them -> a human reviews -> final set.**

- **`query_candidates_{factual,comparative,longitudinal}.jsonl`** - the raw generated candidate questions, split by question type.
- **`query_grounded_{...}.jsonl`** - those candidates after **grounding**: each question is matched to the transcript chunks that answer it, and any question no chunk supports is thrown out.
- **`query_scored_{...}.jsonl`** - the grounded questions after automatic scoring for wording leakage and naturalness/quality.
- **`query_review_{...}.csv`** - the spreadsheets a human used to keep, cut, or reword each candidate.
- **`queryset_core.jsonl`** - the final, hand-picked **core** set: a small, high-quality set of questions (committed to git).
- **`queryset_broad.jsonl`** - the final, larger **broad** set for wider coverage (committed to git).
- **`generation_conditions.md`** - a plain-language record of the exact settings this set was generated and selected under, written for the methods section of the writeup (committed to git).

## 4. Diagnostic-era reference answers - an early experiment, kept for reference

An early attempt at building the "answer key" (what a correct answer should contain).

- **`nuggets_draft_core.jsonl`** - draft "gold" facts that a correct answer to each core question should include, along with a model-written reference answer.
- **`gate_sample.md`** - a readable sample of those drafted facts, used to sanity-check the approach.
